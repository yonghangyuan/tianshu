## 二、创新点矩阵

### 创新点 1：四级决策审计模型（核心）

| 级别 | 内容 | 触发条件 | 传统框架 |
|------|------|----------|:---:|
| L1 BASIC | 决策 ID + 时间戳 | 所有决策 | Hermes/OpenClaw 有类似 |
| L2 SNAPSHOT | 世界状态快照 | 工具调用 | ❌ 独家 |
| L3 FULL | LLM 推理链 | 深度推理 | ❌ 独家 |
| L4 EVALUATED | 事后评估+根因 | 故障回溯 | ❌ 独家 |

**创新表述**: 首次将高可信软件的"行为可追溯"原则系统化应用于 LLM Agent 决策链路。

### 创新点 2：因果链追溯

```
用户请求
  └→ decision_A (路由: 为什么选 DS v4-pro?)
       └→ decision_B (工具调用: 为什么选 shell_exec?)
            └→ decision_C (重试: 为什么换策略?)
```

不是线性日志——是**有向无环图**。parent_id/child_id 关联，支持从任意节点向上追溯。

**创新表述**: Agent 决策的因果图建模——区别于传统框架的扁平日志。

### 创新点 3：审计驱动的故障定位

| 场景 | 无审计 | 有天曜 |
|------|--------|--------|
| Agent 调用 10 个工具后空回复 | 翻完整对话日志 10+ 分钟 | 查 L3 推理链 → 30 秒定位根因 |
| Windows 上 shell_exec 全部失败 | 逐条看错误信息 | L2 快照显示 cwd=/workspace → 1 秒定位 |

```
题目: 天曜——面向自主AI Agent的高可信四级决策审计框架

摘要 (200-250字)
关键词: AI Agent; 决策审计; 高可信软件; 三爻架构

1. 引言 (2页)
  1.1 研究背景: LLM Agent 在生产环境中的可信挑战
  1.2 问题定义: Agent 决策的黑盒问题
  1.3 本文贡献: ①四级审计模型 ②因果链追溯 ③工程验证

2. 理论基础 (1.5页)
  2.1 高可信软件架构理论 (王戟 2024)
    - 核心原则: 可追溯 · 可复现 · 可归因
    - 传统应用: 操作系统内核 · 安全关键系统
  2.2 从确定性软件到概率性 Agent
    - 传统软件: 行为由代码决定 → 静态分析可行
    - AI Agent: 行为由 LLM 推理决定 → 需要新的审计范式
  2.3 三爻设计哲学
    - 天爻(规律): 审计 + 因果链
    - 人爻(目的): 意图理解 + 决策归因
    - 地爻(物质): 执行追踪 + 效果评估

3. 四级决策审计模型 (2页)
  3.1 模型定义
    - L1 BASIC: decision_id + timestamp
    - L2 SNAPSHOT: 文件系统快照 + 环境变量 + 工具列表
    - L3 FULL: LLM reasoning_content + 工具调用链 + 参数
    - L4 EVALUATED: 实际结果 vs 预期 · 差异分析 · 根因定位
  3.2 审计触发策略
    - 基于任务类型的自适应审计级别
    - 高风险操作强制 L3 审计
  3.3 存储与查询
    - SQLite audit_records + causal_chain 双表
    - 支持按 session_id / task_type / model 多维度查询

4. 系统实现 (2页)
  4.1 天枢 Agent 框架架构
    - AgentCore.run_stream() 的审计注入点
    - decision_id 的生命周期
  4.2 因果链实现
    - parent_id / child_id 的关联机制
    - 跨 session 的因果关系追踪
  4.3 工程指标
    - 审计开销: < 5% 响应时间增加
    - 存储开销: ~2KB/decision (L3)

5. 实验与评估 (2页)
  5.1 实验设计
    - 15 个典型 Agent 任务（搜索/文件操作/代码生成）
    - 故意注入 5 类故障（网络错误/权限错误/模型幻觉/工具失败/环境不兼容）
  5.2 故障定位效率
    - 有审计 vs 无审计（纯对话日志）
    - 5 名开发者独立定位 10 个故障
  5.3 审计覆盖率
    - L3 审计覆盖了 X% 的关键决策节点
  5.4 与现有框架对比
    - Hermes Agent / OpenClaw / LangChain 审计能力矩阵

6. 案例分析 (1页)
  "杀伤网搜索"案例的完整审计追踪展示

7. 相关工作 (0.5页)
  AI Agent 框架 · AI 安全 · 可解释 AI · 软件审计

8. 结论与展望 (0.5页)

参考文献
```

## 四、实验设计方案

### 4.1 故障注入集（5 类 × 3 实例 = 15 个任务）

| 故障类型 | 任务示例 | 预期根因 |
|----------|----------|----------|
| 网络错误 | 搜索时 API 超时 | L1 时间戳异常 + L2 网络状态 |
| 权限错误 | 写入系统目录 | L2 快照定位权限问题 |
| 模型幻觉 | LLM 虚构文件路径 | L3 推理链暴露幻觉 |
| 工具失败 | shell_exec WinError 267 | L2 环境快照 + L3 推理链 |
| 环境不兼容 | Linux 命令在 Windows 执行 | L2 OS 快照 |

### 4.2 评估指标

```
指标 1: 故障定位时间 (MTTD)
  - 无审计组: 平均 N 分钟
  - 天曜组: 平均 M 秒
  - 提升: (N - M) / N × 100%

指标 2: 根因准确率
  - 开发者定位的根因是否与注入的故障一致

指标 3: 审计完整性
  - 关键决策节点被审计的比例

指标 4: 系统开销
  - 审计带来的额外延迟和存储
```

| 资源 | 数量 | 说明 |
|------|:---:|------|
| 开发者被试 | 5 人 | 同实验室同学即可 |
| 故障任务 | 15 个 | 5 类 × 3 实例 |
| 对比系统 | 2 个 | Hermes Agent + 无审计天枢（消融实验） |

## 五、竞争优势分析

### 5.1 vs 其他 AI Agent 论文

| 论文类型 | 常见套路 | 我们的差异化 |
|----------|----------|-------------|
| "XX Agent: 一个新的框架" | 架构描述 + 跑分 | ❌ 太普通 |
| "基于 LLM 的 XX 应用" | 调 API + 调 prompt | ❌ 无技术深度 |
| "LLM Agent 的安全问题" | 综述/调研 | ❌ 无系统实现 |
| **本文** | 理论迁移 + 系统实现 + 实验验证 | ✅ 三位一体 |

### 5.2 评委可能的质疑 & 应答

| 质疑 | 应答 |
|------|------|
| "这不就是日志系统吗？" | 日志是扁平的，审计是结构化的因果图。关键差异：日志告诉你"发生了什么"，审计告诉你"为什么发生"和"谁该负责" |
| "跟 LangSmith 有什么区别？" | LangSmith 是商业产品，不可自部署，数据出境。天曜是开源、本地、符合高可信标准的审计系统 |
| "四级模型有必要吗？" | L1-L2 是基础保障，L3-L4 是差异化价值。消融实验证明每一级的作用 |
| "案例太少" | 15 个受控实验 + 1 个真实案例分析，覆盖主要故障类型 |
